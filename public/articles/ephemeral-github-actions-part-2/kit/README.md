# GitHub Actions на временных VPS

Самодостаточный учебный комплект к второй части статьи. Он поднимает VPS в Timeweb Cloud под один job, публикует пакет в приватный S3, независимо проверяет байты и удаляет VPS, IPv4 и runner.

Первый запуск собирает маленькую HTML-страницу из `repository/demo.py`. Для этого не нужен клиентский код, Android SDK или Vault. После сквозной проверки вместо демо подключается свой проект. Скриншоты Android и Backend в статье относятся к ранее проверенной проектной реализации, а не к запуску этого комплекта.

## Что проверено

13 ноября 2026 комплект установлен с нуля на Ubuntu 24.04 x86_64 в отдельном проекте Timeweb. Для проверки созданы новый приватный репозиторий, GitHub App, сеть, бакет и два S3-пользователя.

| Сценарий | Подтверждённый результат |
| --- | --- |
| Обычный push | Test, Build и Publish прошли. Control скачал архив, сверил SHA-256, размер и исходный коммит. `accepted=true` |
| Файл `FAIL_DEMO` | Тест упал, Build и Publish пропущены. В префиксе аренды нет объектов |
| Отмена во время `sleep 120` | Работающий job отменён, пакет не опубликован |

Во всех трёх сценариях VPS, IPv4 и регистрация runner удалились автоматически, журнал подтвердил `closed=true`. Первый прогон выявил ошибку порядка cloud-init — её исправляет `defer: true` в `write_files`. Команды оператора теперь дожидаются блокировки журнала, а не завершаются без вывода. Workflow использует закреплённый checkout 7.0.1 на Node 24.

Финальный успешный прогон выполнен на коде из этого архива. После проверки удалены Control, сеть, бакет и тестовый репозиторий, все выпущенные для стенда доступы отозваны.

Отдельно проходят 26 локальных Python-тестов, проверка состава ZIP и синтаксиса установщика. Они не создают облачных ресурсов.

## Что понадобится

- Отдельный Control с Ubuntu 24.04 x86_64, Python 3.12 и systemd. Достаточно небольшой машины с 2 ГиБ памяти и местом для скачанных результатов. Она не собирает приложение.
- Аккаунт Timeweb Cloud с балансом, отдельный проект временных VPS и приватный S3-бакет в `ru-1`.
- Собственный приватный репозиторий GitHub и права создания GitHub App. Ветка `dev` содержит только проверенный код команды. PR и fork в этом комплекте не допускаются.
- Исходящие HTTPS-соединения с Control к GitHub API и Timeweb/S3, а с worker — к GitHub и S3. Зеркалам пакетов Ubuntu нужны HTTP и HTTPS. Открывать входящий порт на Control для webhook не нужно.

## Файлы и ответственность

| Файл | Назначение |
| --- | --- |
| `controller.py` | Диспетчер, SQLite-журнал, отдельные команды очистки и проверки S3 |
| `clients.py` | GitHub App, Timeweb API, короткие S3-ссылки и независимое чтение |
| `bootstrap.py` | Установка и регистрация runner на новой VPS |
| `worker.py` | Проверка назначенного job, упаковка и публикация результата |
| `install.sh` | Установка Control без включения таймеров |
| `systemd/` | Три таймера и одна параметризованная служба |
| `prepare.py` | Подстановка своего репозитория и SHA, расчёт хешей workflow |
| `repository/` | Полный демопроект и оба workflow, включая скрытую `.github` |
| `tests/` | Проверки без аренды машин |

## 1. Создать проект облака и S3

В панели Timeweb создайте отдельный проект для временных машин. Сохраните его числовой ID. Выпустите токен только для этого проекта с управлением облачными серверами и сетями, остальные права отключите. Разрешите удаление через API без подтверждения в Telegram. Для баланса выпустите отдельный токен только с правами финансов. У Timeweb это уровень «Управление», но финансовый клиент комплекта выполняет только GET.

В разделе «Сети» создайте отдельную приватную сеть CI в той же зоне, где будут серверы. Сохраните её ID вида `network-…` для `cloud.network_id`. Не выбирайте сеть рабочих серверов — одного отдельного проекта для сетевой изоляции недостаточно. Control и временные VPS размещаем в новой сети.

Создайте приватный бакет в `ru-1`, выберите тестовый проект и отключите автоматическое увеличение тарифа. В разделе пользователей S3 добавьте двух отдельных пользователей, каждому разрешите только этот бакет:

- `ci-writer` с уровнем «Чтение и запись».
- `ci-reader` с уровнем «Чтение».

Скопируйте Access Key и Secret Key каждого пользователя в защищённое место. Главного пользователя S3 с доступом ко всем бакетам здесь не используем.

В жизненном цикле бакета задайте удаление объектов с префиксом `ephemeral-ci/` через семь дней. Если включаете версионирование, добавьте удаление неактуальных версий. Проверка вместимости считает все версии, а не только последние.

## 2. Подготовить репозиторий и GitHub App

Создайте приватный репозиторий и ветку `dev`. Сначала добавьте в неё только два файла из комплекта:

- `repository/demo.py` в корень репозитория как `demo.py`.
- `repository/.github/workflows/auto-build.yml` по тому же пути без префикса `repository/`.

Сохраните изменения обычным коммитом и отправьте их на GitHub. Сам `auto-build.yml` имеет событие `workflow_call` и пока не запускается. Скопируйте полный SHA этого коммита из GitHub либо командой `git rev-parse HEAD` в своём репозитории.

На своём компьютере в распакованном комплекте выполните подготовку caller workflow, подставив свои два значения:

```sh
python3 prepare.py --repository YOUR_ORG/YOUR_REPO --reusable-sha FULL_COMMIT_SHA
```

Команда меняет только локальный `repository/.github/workflows/auto-ci.yml` и выводит SHA-256 обоих workflow. Сохраните эти два хеша для конфигурации Control. Добавьте получившийся `auto-ci.yml` в `.github/workflows/` своего репозитория, сохранив точные байты файлов и окончания строк LF.

В настройках репозитория откройте Secrets and variables → Actions → Variables. Создайте repository variable `CI_ENABLED` со значением `false`. Это переменная, а не secret. Включим её после подготовки Control.

В настройках аккаунта или организации создайте GitHub App. Отключите Webhook и задайте Repository permissions:

- Actions — Read and write.
- Administration — Read and write.
- Contents — Read-only.

Установите App только в созданный репозиторий. Сохраните App ID, Installation ID и сгенерированный private key. App ID есть на странице приложения, Installation ID — в адресе страницы установленного приложения после `/installations/`.

Не изменяйте pin на ветку или `latest`. Изменение reusable workflow требует нового коммита, нового pin в caller и новых одобренных хешей на Control.

Для повторной подстановки возьмите чистый `repository/.github/workflows/auto-ci.yml` из исходного ZIP. Рядом положите новую версию `auto-build.yml` и снова выполните `prepare.py` с её SHA. Уже подготовленный caller программа намеренно не перезаписывает.

## 3. Установить Control

В тестовом проекте создайте небольшую VPS с Ubuntu 24.04 x86_64 и 2 ГиБ RAM. Выберите отдельную сеть CI из шага 1 и публичный IPv4. Для эксперимента отключите автоматические бэкапы и дополнительные платные услуги. Подключитесь своим SSH-ключом либо откройте «Консоль» сервера в панели Timeweb.

На Control скачайте исходный ZIP и соседний файл `.sha256`, проверьте архив и распакуйте. Не переносите сюда изменённую командой `prepare.py` папку из шага 2. Команды этого раздела выполняются на выделенном Control, не на worker и не на production-сервере:

```sh
sha256sum -c ephemeral-ci-kit-v1.zip.sha256
python3 -m zipfile -e ephemeral-ci-kit-v1.zip .
cd ephemeral-ci
sha256sum -c SHA256SUMS
sudo bash install.sh
```

Установка кладёт программы в `/opt/ephemeral-ci`, конфигурацию в `/etc/ephemeral-ci`, журнал в `/var/lib/ephemeral-ci`. Она создаёт Python venv, устанавливает зависимости и systemd units. Таймеры остаются выключенными. Повторная установка поверх существующей конфигурации запрещена.

Поместите GitHub App private key в `/etc/ephemeral-ci/github-app.pem`, токены Timeweb — в `/etc/ephemeral-ci/timeweb.token` и `/etc/ephemeral-ci/finance.token`. Файлы токенов содержат только соответствующее значение, без `Bearer` и кавычек.

Создайте `/etc/ephemeral-ci/s3-writer.json` и `/etc/ephemeral-ci/s3-reader.json`. В каждом один JSON-объект, значения берутся у соответствующего пользователя S3:

```json
{
  "aws_access_key_id": "FILL_ME",
  "aws_secret_access_key": "FILL_ME"
}
```

Все пять файлов принадлежат root и имеют права `0600`. Заполняйте их через защищённый редактор, не добавляйте в Git. Например, `sudoedit /etc/ephemeral-ci/s3-reader.json`. Затем:

```sh
sudo chown root:root /etc/ephemeral-ci/*
sudo chmod 600 /etc/ephemeral-ci/*
```

## 4. Заполнить конфигурацию и проверить доступы

Откройте `sudoedit /etc/ephemeral-ci/config.json`. Сначала заполните `github.app_id`, `installation_id`, `repository`. Приватный ключ App и токен проекта должны быть уже установлены. Остальные поля можно заполнить после чтения каталога:

```sh
sudo /opt/ephemeral-ci/venv/bin/python -I -B /opt/ephemeral-ci/controller.py catalog
```

Команда выводит ID репозитория, доступные тарифы VPS и образы ОС. Она ничего не заказывает. Выберите Ubuntu 24.04 x86_64 и подходящий preset — для демо начните с 2 vCPU и 4 ГиБ RAM. Зону доступности возьмите из панели Timeweb для выбранного тарифа.

Заполните оставшиеся поля:

| Поле | Значение |
| --- | --- |
| `github.repository_id` | Числовой ID из `catalog` |
| `github.reusable_sha` | SHA первого коммита из шага 2 |
| `github.workflow_sha256` | Два хеша, выведенных `prepare.py` |
| `cloud.project_id` | ID отдельного проекта временных VPS |
| `cloud.preset_id`, `os_id`, `availability_zone` | Выбранные тариф, Ubuntu и зона |
| `cloud.network_id` | ID отдельной сети CI из шага 1, в той же зоне |
| `cloud.max_vm_monthly_rub` | Максимальная одобренная месячная цена выбранного VPS |
| `s3.bucket` | Имя приватного бакета |
| `s3.capacity_bytes` | Оплаченная ёмкость бакета в байтах |
| `limits.ipv4_monthly_rub` | Текущая месячная цена одного IPv4 из панели |
| `limits.storage_monthly_rub` | Текущая месячная цена бакета |
| `limits.egress_rub_per_gb` | Текущая цена исходящего S3-трафика |
| `limits.approved_until` | UTC-срок проверки этих цен, например результат команды ниже |

Окно согласования цен ограничено семью днями. Для первого запуска удобно дать одни сутки:

```sh
date -u -d '+1 day' '+%Y-%m-%dT%H:%M:%SZ'
```

Первоначально `max_leases_total=1` и `budget_rub=reserve_rub=300`. Это лимит одного заказа и консервативный резерв, не обещание суммы счёта. Журнал не возвращает резерв после удаления VPS. Полная оценка включает время машины и IP, бакет, трафик и запас на очистку. Если выбранный тариф в неё не помещается, `check` остановится до заказа.

Стоимость VPS и баланс считываются из API перед созданием. Цены IP, S3 и трафика вводятся по проверенному тарифу и ограничены `approved_until`. При потере Control или недоступном API удаление может задержаться, поэтому этот резерв не является жёстким биллинговым лимитом провайдера.

Для демо оставьте остальные значения по умолчанию. Выполните:

```sh
sudo /opt/ephemeral-ci/venv/bin/python -I -B /opt/ephemeral-ci/controller.py check
```

Ожидаемый ответ — `CHECK_OK`. Эта команда проверяет конфигурацию, ID репозитория, тариф, баланс, два разных S3-пользователя и вместимость бакета. VPS она не создаёт.

## 5. Запустить службы в правильном порядке

Сначала включите очистку и независимое чтение:

```sh
sudo systemctl enable --now ephemeral-ci-cleanup.timer ephemeral-ci-readback.timer
sudo systemctl start ephemeral-ci@cleanup.service
```

В `/etc/ephemeral-ci/config.json` замените `enabled` на `true`. Проверьте конфигурацию ещё раз и включите диспетчер:

```sh
sudo /opt/ephemeral-ci/venv/bin/python -I -B /opt/ephemeral-ci/controller.py check
sudo systemctl enable --now ephemeral-ci-dispatch.timer
sudo systemctl list-timers 'ephemeral-ci-*'
```

Без свежего heartbeat очистки и её отдельного подтверждения записи аренды диспетчер не отправит POST создания VPS. До появления разрешённого queued job расходы на worker не возникают.

## 6. Выполнить первый сквозной запуск

На GitHub установите `CI_ENABLED=true` и отправьте новое изменение `demo.py` в `dev`. Предыдущий пропущенный job не превратится в queued автоматически — нужен новый push.

Ожидаемая последовательность:

1. В Actions появился ожидающий `build`.
2. В журнале Control появились `reserved`, затем `acknowledged` и `create_sent`.
3. В Timeweb появился сервер с именем `ci-…`, GitHub получил runner с тем же именем.
4. Job выполнил Test, Build и Publish verified output.
5. В S3 появились `ephemeral-ci/ci-…/result.tar.gz` и последний `delivery.json`.
6. Control скачал и проверил пакет, VPS и IPv4 удалились.

Проверка состояния и журналов:

```sh
sudo /opt/ephemeral-ci/venv/bin/python -I -B /opt/ephemeral-ci/controller.py status
sudo journalctl -u 'ephemeral-ci@*.service' --since '30 min ago' --no-pager
```

У принятого запуска `conclusion="success"`, `closed=true`, `readback=true`, `accepted=true`. Проверенный архив лежит в `/var/lib/ephemeral-ci/results/ci-….tar.gz`. На Control он не распаковывается и не исполняется. В панели облака отдельно проверьте отсутствие VPS и IP, а в GitHub Settings → Actions → Runners — отсутствие временного runner.

## 7. Проверить ошибку, отмену и остановку

Каждая следующая попытка расходует ещё один резерв. После первой приёмки для двух дополнительных проверок явно увеличьте `max_leases_total` до 3 и `budget_rub` до 900, сохранив исходный журнал. Перед изменением лимитов снова проверьте тарифы и баланс.

- Ошибка проверки. Добавьте в корень деморепозитория файл `FAIL_DEMO` и отправьте изменение в `dev`. Тест упадёт, `delivery.json` не появится, VPS/IP/runner будут закрыты. Перед удалением этого файла установите `CI_ENABLED=false`, чтобы подготовительный push не создал лишний запуск.
- Отмена. Пока `CI_ENABLED=false`, удалите `FAIL_DEMO`, добавьте перед Test временный шаг `run: sleep 120`, закрепите новую версию reusable workflow, обновите caller и хеши Control. Затем включите `CI_ENABLED=true` и отправьте одно изменение демо. Отмените job через GitHub после старта runner. Ресурсы должны закрыться без принятого пакета. Изменение workflow без обновления хешей будет отклонено до заказа VPS.
- Перезапуск Control-служб не меняет исходное время аренды. Если есть активная машина, можно перезапустить только dispatch unit и проверить, что она не дублируется.

Чтобы прекратить новые заказы и закрыть текущую аренду:

```sh
sudo /opt/ephemeral-ci/venv/bin/python -I -B /opt/ephemeral-ci/controller.py stop
sudo systemctl stop ephemeral-ci-dispatch.timer
```

Очистку не выключайте, пока `status` не покажет `closed=true` у всех записей. После проверки отсутствия машин и IP можно остановить остальные таймеры. `resume` снимает локальный STOP только при отсутствии открытых аренд; лимиты и историю он не сбрасывает.

```sh
sudo systemctl disable --now ephemeral-ci-cleanup.timer ephemeral-ci-readback.timer
```

Control и бакет не удаляются автоматически. Если весь контур создавался только для эксперимента, после закрытия всех аренд выполните следующие действия:

1. Сохраните нужные результаты и журнал Control. Установите `CI_ENABLED=false`.
2. Удалите Control и отдельно его публичный IPv4. Проверьте список IP, а не только серверов.
3. Удалите объекты тестового бакета, включая версии и маркеры удаления, затем сам бакет и обоих тестовых S3-пользователей.
4. Удалите отдельную сеть CI и пустой тестовый проект.
5. Удалите тестовую GitHub App вместе с установкой и ключами, отзовите оба токена Timeweb.
6. Удалите ненужный деморепозиторий и локальные копии тестовых секретов.

Рабочие проекты, общие сети, бакеты и доступы в этот список не входят.

## Как устроены ошибки и восстановление

| Состояние | Действие |
| --- | --- |
| `Workflow changed` | Сверить два файла, pin reusable и одобренные хеши. Не отключать проверку |
| `Cleanup heartbeat is stale` | Проверить `ephemeral-ci-cleanup.timer` и журнал cleanup unit |
| VPS готова, job остаётся queued | В консоли этой VPS выполнить `cloud-init status --long` и `journalctl -u ci-runner -n 30 --no-pager`. Если GitHub потерял сессию и удалил регистрацию, отменить run, дождаться `closed=true` на Control и отправить новый push |
| `create_sent` без успешного ответа API | Не повторять POST. Очистка ищет машину по уникальному имени, комментарию и проекту |
| `Create result remains uncertain` | Проверить операцию у провайдера и сопоставить ресурсы. Слот и резерв сохраняются, автоматического «сброса» нет |
| `Recorded IP has been reassigned` | Не удалять чужой IP. Проверить, кто перепривязал ресурс |
| `closed=true`, `readback=false` при success | Читать журнал readback. Проверить права S3-reader, наличие двух объектов, размер и SHA-256 |
| `cleanup_overdue=true` | Вручную проверить строго свои записанные VM/IP ID и восстановить доступ Control к API. Не удалять весь проект |

Не удаляйте `state.sqlite3` для повторной попытки. Это одновременно журнал владельцев ресурсов, запрет повторного POST и учёт всех резервов. В неопределённом случае комплект намеренно сохраняет запись вместо автоматического объявления успеха.

## Подключить свой Android или Backend

После приёмки демо замените шаги Test и Build в `auto-build.yml` командами своего проекта. Всё, что нужно сохранить, положите в `out/`. Последний шаг `worker.py publish out` остаётся прежним.

Подготовка runner в этом комплекте устанавливает Python и зависимости GitHub runner. Java, Android SDK, Node.js или Docker добавляются в `bootstrap.py` под версии вашего проекта. После изменения bootstrap обновите файлы Control в остановленном состоянии, не затрагивая открытые аренды. Для AAB увеличьте `max_artifact_bytes` и проверьте оплаченный объём S3 и резерв трафика.

Новый reusable workflow закрепляется новым полным SHA, а оба хеша повторно заносятся в конфигурацию Control. Для нового репозитория создайте отдельную конфигурацию и отдельный журнал, не переиспользуйте живую аренду.

Подпись Android и Vault не входят в демопроект — это отдельная интеграция с секретами конкретного приложения. Базовая практика не требует ни Vault, ни signing key. В проектном примере статьи они показаны как расширение уже работающего контура, а не скрытая зависимость этого архива.

## Границы модели доступа

Ключи Timeweb, GitHub App и постоянные S3-ключи остаются на Control. Worker получает короткий registration token и две подписанные PUT-ссылки только на свои объекты. Они истекают по исходному времени очистки. Провайдер может сохранять cloud-init до удаления VPS; переданные значения ограничены по сроку.

Ограничение размера пакета проверяет `worker.py`, затем независимо reader. Подписанная PUT-ссылка не ограничивает размер на стороне S3. Поэтому этот контур рассчитан на доверенный DEV-код, а не на запуск посторонних PR. Секреты приложения не добавлены в демо.

Удаление и диспетчер — отдельные timer units на одном Control. Они используют короткую общую блокировку для одного прохода, не на время сборки. Зависший проход ограничен `TimeoutStartSec=120`. Потеря самого Control остаётся общей точкой отказа.

Проверенные архивы сохраняются локально до ручного удаления. В отличие от проектной версии, здесь нет автоматического хранения только двух последних кандидатов. Следите за свободным диском Control; S3-retention настраивается отдельно в шаге 1.

## Проверки без облака

В каталоге распакованного комплекта:

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -B -m unittest discover -s tests -v
bash -n install.sh
```

Тесты проверяют успешный цикл, ошибку, отмену, запрет дубликатов, потерянный ответ создания, неизменный срок, отключение GitHub, перепривязанный IP, чужой workflow, хеши и маркер S3. Это локальные проверки, не запуск Timeweb и не выполненная продуктовая сборка.
